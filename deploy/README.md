# Развёртывание ZT Lab

Схема работы:

```
интернет ──443──▶ VPS (nginx, TLS) ──WireGuard──▶ ноутбук (Node, SQLite, 3D-файлы)
```

Наружу открыт только VPS и только порт 443. База и 3D-файлы физически
остаются на ноутбуке, в интернет не отдаются.

Почему так: VPS нужен только чтобы принять HTTPS-соединение и
передать его по закрытому туннелю. Данные не копируются наружу, поэтому
утёчка с VPS невозможна.

Домен выбран и свободен: DNS-записей нет, сайта по нему не отвечает.
Прописан прямо в `deploy/nginx-ztlab.conf` и в команде выпуска сертификата.

> ⚠️ **`ztlab.ru` использовать нельзя.** Это работающая зуботехническая
> лаборатория в Москве: WordPress на PHP, IP 87.236.16.35, действующий
> сертификат Let's Encrypt. Направлять на него DNS — значит перехватить
> чужой работающий сайт.

Перед покупкой VPS проверьте, что `ztbase.ru` действительно свободен
**в регистраторе**: отсутствие DNS-записей этого не доказывает, домен
может быть зарегистрирован и просто без сайта.

## 1. Node 22 — почему именно он

`better-sqlite3` — нативный модуль, у него готовой сборки под Node 26 нет,
а исходники не компилируются: в Node 26 движок V8 убрал `info.This()`.

Node 22 — актуальная LTS, под неё есть готовые сборки. Версия закреплена
в трёх местах, чтобы расхождение было невозможно:

- `.nvmrc` — файл `22`
- `package.json` → `"engines": { "node": "22.x" }`
- `package.json` → цели сборки `pkg` переведены на `node22`

Все зависимости в `package.json` закреплены точными версиями, без `^`.
Установка идёт через `npm ci`, которая берёт версии из `package-lock.json`.
Результат на любой машине одинаковый.

Проверка: `cat .nvmrc && node -v`

## 2. Установка на ноутбук

```bash
sudo ./deploy/install-laptop.sh
```

Скрипт создаёт пользователя `ztlab` (без прав в системе), кладёт код
в `/opt/ztlab`, данные — в `/var/lib/ztlab`, генерирует `SESSION_SECRET`.

Код и данные разнесены намеренно: обновление кода не должно задевать
базу и 3D-файлы.

Конфигурация лежит в `/etc/ztlab/ztlab.env`, права `640`, владелец
`root:ztlab` — секрет не должен попасть в общий доступ.

## 3. WireGuard

Смысл: VPS и ноутбук соединяются напрямую, минуя интернет.

### На ноутбуке

```bash
sudo apt install wireguard
sudo wg genkey | sudo tee /etc/wireguard/laptop.key | sudo wg pubkey | sudo tee /etc/wireguard/laptop.pub
```

Скопируйте шаблон и подставьте ключи:

```bash
sudo cp deploy/wireguard/wg0.conf.laptop /etc/wireguard/wg0.conf
sudo chmod 600 /etc/wireguard/wg0.conf
sudo nano /etc/wireguard/wg0.conf   # PrivateKey из laptop.key
sudo systemctl enable --now wg-quick@wg0
```

Ключ VPS подставите на следующем шаге.

`AllowedIPs = 10.8.0.0/24` — через VPN идёт только связь с VPS,
обычный интернет напрямую и быстрее.

### На VPS

```bash
sudo ./deploy/wireguard/setup-wireguard-vps.sh <публичный_ключ_ноутбука>
```

Скрипт сгенерирует ключи VPS, поднимет туннель, настроит файрвол
(наружу только 22, 80, 443) и напечатает публичный ключ VPS.

**Порт WireGuard (51820) наружу не открывается** — туннель работает
между двумя конкретными адресами.

### Проверка

```bash
# на ноутбуке
ping 10.8.0.1
ip addr show wg0        # запомнить адрес, он пойдёт в HOST

# на VPS
wg show
ping 10.8.0.2
```

## 4. nginx на VPS

```bash
sudo apt install -y nginx
sudo cp deploy/nginx-ztlab.conf /etc/nginx/sites-available/ztlab
sudo nano /etc/nginx/sites-available/ztlab   # заменить 10.8.0.2, если адрес ноутбука другой
sudo ln -s /etc/nginx/sites-available/ztlab /etc/nginx/sites-enabled/
sudo rm -f /etc/nginx/sites-enabled/default
```

Сертификата ещё нет, поэтому `nginx -t` сперва ругнётся. Это ожидаемо,
шаг 5.

В конфиге обратите внимание:

- `client_max_body_size 512m` — под крупные STL;
- `proxy_set_header X-Forwarded-For` — без него приложение не увидит
  реальный адрес сотрудника и ограничение попыток входа станет общим
  на всю лабораторию;
- `/health` отдаёт статус без входа — для проверки и мониторинга.

## 5. Сертификат

DNS для `ztbase.ru` должен указывать на IP VPS. Затем:

```bash
sudo apt install -y certbot python3-certbot-nginx
sudo certbot --nginx -d ztbase.ru -d www.ztbase.ru
```

Certbot сам поправит конфиг и договорится о продлении. Проверьте:
`sudo certbot renew --dry-run`.

## 6. Запуск на ноутбуке

Впишите в `/etc/ztlab/ztlab.env` адрес из `ip addr show wg0`:

```
HOST=10.8.0.2
COOKIE_SECURE=1
```

```bash
sudo systemctl start ztlab
sudo systemctl status ztlab
```

Если не поднялся — `sudo journalctl -u ztlab -n 50`.

## 7. Проверка

```bash
# с ноутбука
curl http://10.8.0.2:3000/health          # {"status":"ok",...}

# с VPS
curl http://10.8.0.2:3000/health          # туннель работает

# снаружи, после сертификата
curl https://ztbase.ru/health
```

Дальше в браузере: `https://ztbase.ru/register` — регистрация первой
лаборатории и администратора.

Проверьте с телефона, что интерфейс пригоден для работы: в лаборатории
им пользуются с телефона, а два старых шаблона рассчитаны на десктоп.

## 8. Бэкапы

```bash
sudo ./deploy/backup.sh

# ежедневно в 3:17 (не в ровный час — чтобы не совпадать с другими задачами)
sudo crontab -e
17 3 * * * /opt/ztlab/deploy/backup.sh >> /var/log/ztlab-backup.log 2>&1
```

Копии в `/var/backups/ztlab`, хранятся 30 последних баз и 30 дней файлов.
Проверьте, что копии на месте и в них есть данные:

```bash
ls -lh /var/backups/ztlab/
sqlite3 /var/backups/ztlab/exo-*.db "SELECT COUNT(*) FROM files;"   # последняя
```

**Одно слабое место:** бэкапы лежат на том же ноутбуке. Пока ноутбук
не потерян — риска нет, но копия должна быть и на VPS. Это стоит
настроить отдельным шагом, например через `rsync` по расписанию.

## Обновление

```bash
git pull
sudo ./deploy/deploy.sh
```

Скрипт проверит версию Node и наличие секрета, снимет копию базы,
обновит код, выполнит `npm ci`, перезапустит сервис и проверит `/health`.

Откат: `git log`, затем `git checkout <коммит>` и `sudo ./deploy/deploy.sh`.
Копия базы перед обновлением снимается автоматически.

## Перенос 3D-файлов в S3

Пока файлы на диске ноутбука. Если ноутбук нельзя держать включённым
или диска не хватает, переключается без правки кода:

```
STORAGE_BACKEND=s3
S3_ENDPOINT=https://storage.yandexcloud.net
S3_BUCKET=ztlab-files
S3_KEY_ID=...
S3_KEY_SECRET=...
```

Своё хранилище в РФ важно: названия файлов могут содержать фамилии
пациентов, и данные не должны уходить за границу.

Перенос выполняется скриптом (отдельно), потому что файлов может быть
много, а процесс должен быть возобновляемым.

## Что закрыто и что нет

Закрыто: пароли (scrypt), разделение лабораторий на уровне запросов,
роли, ограничение попыток входа, HTTPS на VPS, брандмауэр,
запрет кэша авторизованных страниц, сессии в SQLite, бэкапы.

Не сделано и требует внимания перед запуском:

- **нет ограничения размера лаборатории.** Квота `STORAGE_QUOTA_GB`
  в конфиге есть, но не проверяется. Без неё лаборатория может занять
  весь диск.
- **нет срока действия триала и тарифов.** Нужно для оплаты.
- **нет восстановления пароля.** Сейчас пароль можно сменить только
  через администратора лаборатории.
- **удаление файла доступно любому сотруднику** (за кодом подтверждения).
  Решение осознанное: админ не всегда на связи, заказ не должен встать.
- **интерфейс не адаптирован под телефон.** Два шаблона по 700 строк
  рассчитаны на десктоп. Лаборатория пользуется с телефона.
