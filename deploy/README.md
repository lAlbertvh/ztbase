# Развёртывание ZT Lab

## Целевая схема

Приложение живёт на VPS рядом с nginx, а ноутбук становится рабочей
машиной и стендом:

```
интернет ──443──▶ VPS (nginx + TLS ─▶ 127.0.0.1:3000 Node ─▶ SQLite, 3D-файлы)
```

Почему так: в прошлой схеме приложение держалось на ноутбуке, а VPS
пробрасывал к нему туннель. Пока ноутбук включён — работает, выключил —
публичный сайт отдаёт 502, и никто об этом не узнаёт, пока не позвонит
клиент. Данные лежали там же, где и бэкапы, что тоже риск: потеря
ноутбука означала потерю данных.

Что меняется, а что нет:

- **nginx править не нужно.** `upstream ztlab_app` уже указывает на
  `127.0.0.1:3000` — на этой схеме там просто будет node вместо туннеля.
- **Туннель на VPS больше не нужен** и не ставится.
- Приложение слушает **только `127.0.0.1`**. Порт 3000 наружу не
  открывается: перед приложением стоит nginx, который и держит TLS.
- `deploy/install-vps.sh` ставит Node 22, пользователя `ztlab`,
  каталоги, таймеры бэкапа и проверки живости.

## Нерешённое

- **Квота хранилища.** В `ztlab.env.example` стоит
  `STORAGE_QUOTA_GB=100`, а на VPS диск 25 ГБ. `install-vps.sh` опускает
  квоту до «диск минус 5 ГБ» автоматически, но если диск расширяют —
  значение надо поднять руками.
- **Файлы пациентов на том же диске.** Архив `uploads` ложится рядом с
  оригиналом. `backup.sh` не даёт ему съесть место (пропускает и пишет
  в журнал), но реальное решение — вывозить копии через
  `backup-offsite.sh` на другую машину.

может быть зарегистрирован и просто без сайта.

## Порядок действий

Целевая схема — приложение на VPS, ноутбук как стенд (см. раздел выше).
Ниже порядок именно для неё.

| Шаг | Где | Что |
|-----|-----|-----|
| 1 | ноутбук | снять копию базы и файлов: `deploy/backup.sh` |
| 2 | ноутбук | скопировать базу через `sqlite3 .backup` (НЕ `cp`, см. ниже), `uploads`, `content` на VPS в `/var/lib/ztlab/` |
| 3 | VPS | `sudo deploy/install-vps.sh` — Node 22, пользователь, каталоги, таймеры |
| 4 | VPS | вписать `CONTENT_ADMIN_USER` и `CONTENT_ADMIN_PASS` в `/etc/ztlab/ztlab.env` |
| 5 | VPS | `systemctl start ztlab` и `curl -sf http://127.0.0.1:3000/health` |
| 6 | VPS | `sudo deploy/check.sh ztbase.ru` |
| 7 | ноутбук | вывозить копии на случай потери VPS: `deploy/backup-offsite.sh` |

nginx перенастраивать не нужно: `upstream ztlab_app` уже указывает на
`127.0.0.1:3000`.

### Чего здесь нет и почему

**Базу нельзя переносить обычным `cp`.** Живая база работает в режиме
WAL: рядом с `exo.db` лежит `exo.db-wal`, и на боевой машине он в 10 раз
больше самой базы (1.6 МБ против 163 КБ). `cp exo.db` скопирует только
главный файл и потеряет всё, что не успело записаться в него, — молча,
без всякой ошибки. Копировать надо так:

```bash
sudo -u ztlab sqlite3 /var/lib/ztlab/database/exo.db ".backup '/tmp/exo.db'"
```

или просто забрать готовую копию из `/var/backups/ztlab/` — там она уже
собрана правильно.

**WireGuard не используется.** Провайдер блокирует этот протокол, связь
с VPS идёт обычным SSH поверх TCP — он в этой сети работает стабильно.
Каталог `deploy/wireguard/` и прежняя схема «туннель с ноутбука»
оставлены как история; в целевой схеме туннель не нужен, потому что
приложение и nginx живут на одной машине. Проверять WireGuard нечем и
не нужно.

## 1. Node 22 — почему именно он

`better-sqlite3` — нативный модуль, у него готовой сборки под Node 26 нет,
а исходники не компилируются: в Node 26 движок V8 убрал `info.This()`.

Node 22 — актуальная LTS, под неё есть готовые сборки. Версия закреплена
в трёх местах, чтобы расхождение было невозможно:

- `.nvmrc` — файл `22`
- `package.json` → `"engines": { "node": "22.x" }`
- `package.json` → цели сборки `pkg` переведены на `node22`

Все зависимости в `package.json` закреплены точными версиями, без `^`.
Установка идёт через `npm ci`, которая берёт версии из `package-lock.json`.
Результат на любой машине одинаковый.

Проверка: `cat .nvmrc && node -v`

## 2. Установка на ноутбук

```bash
sudo ./deploy/install-laptop.sh
```

Скрипт создаёт пользователя `ztlab` (без прав в системе), кладёт код
в `/opt/ztlab`, данные — в `/var/lib/ztlab`, генерирует `SESSION_SECRET`.

Код и данные разнесены намеренно: обновление кода не должно задевать
базу и 3D-файлы.

Конфигурация лежит в `/etc/ztlab/ztlab.env`, права `640`, владелец
`root:ztlab` — секрет не должен попасть в общий доступ.

## 3. WireGuard

Смысл: VPS и ноутбук соединяются напрямую, минуя интернет.

### На ноутбуке

```bash
sudo apt install -y wireguard
sudo ./deploy/wireguard/setup-wireguard-laptop.sh <публичный_ключ_VPS>
```

Скрипт создаёт ключи ноутбука (один раз, при повторном запуске
использует существующие), пишет конфигурацию, поднимает туннель
и печатает **публичный ключ ноутбука**. Этот ключ нужно передать
на сервер — без него туннель не поднимется.

`AllowedIPs = 10.8.0.0/24` — через VPN идёт только связь с VPS,
обычный интернет напрямую и быстрее.

### На VPS

```bash
sudo ./deploy/wireguard/setup-wireguard-vps.sh <публичный_ключ_ноутбука>
```

Скрипт сгенерирует ключи VPS, поднимет туннель, настроит файрвол
(наружу только 22, 80, 443) и напечатает публичный ключ VPS.

**Порт 51820/udp открыт наружу — это обязательно.** Ноутбук стоит за
домашним или офисным роутером, то есть снаружи у него нет адреса,
и соединение может установить только он, направив запрос на VPS.
Если закрыть порт, туннель не поднимется никогда.

Наружу открыты ровно четыре порта: 22 (SSH), 80 (только для выпуска
сертификата), 443 (сайт) и 51820/udp (WireGuard).

### Проверка

```bash
# на ноутбуке
ping 10.8.0.1
ip addr show wg0        # запомнить адрес, он пойдёт в HOST

# на VPS
wg show
ping 10.8.0.2
```

## 4. nginx на VPS

```bash
sudo apt install -y nginx
sudo cp deploy/nginx-ztlab.conf /etc/nginx/sites-available/ztlab
sudo nano /etc/nginx/sites-available/ztlab   # заменить 10.8.0.2, если адрес ноутбука другой
sudo ln -s /etc/nginx/sites-available/ztlab /etc/nginx/sites-enabled/
sudo rm -f /etc/nginx/sites-enabled/default
```

Сертификата ещё нет, поэтому `nginx -t` сперва ругнётся. Это ожидаемо,
шаг 5.

В конфиге обратите внимание:

- `client_max_body_size 512m` — под крупные STL;
- `proxy_set_header X-Forwarded-For` — без него приложение не увидит
  реальный адрес сотрудника и ограничение попыток входа станет общим
  на всю лабораторию;
- `/health` отдаёт статус без входа — для проверки и мониторинга.

## 5. Сертификат

DNS для `ztbase.ru` должен указывать на IP VPS. Затем:

```bash
sudo apt install -y certbot python3-certbot-nginx
sudo certbot --nginx -d ztbase.ru -d www.ztbase.ru
```

Certbot сам поправит конфиг и договорится о продлении. Проверьте:
`sudo certbot renew --dry-run`.

## 6. Запуск на ноутбуке

Впишите в `/etc/ztlab/ztlab.env` адрес из `ip addr show wg0`:

```
HOST=10.8.0.2
```

## 8. Бэкапы

```bash
sudo ./deploy/backup.sh

# ежедневно в 3:17 (не в ровный час — чтобы не совпадать с другими задачами)
sudo crontab -e
17 3 * * * /opt/ztlab/deploy/backup.sh >> /var/log/ztlab-backup.log 2>&1
```

Копии в `/var/backups/ztlab`, хранятся 30 последних баз и 30 дней файлов.
Проверьте, что копии на месте и в них есть данные:

```bash
ls -lh /var/backups/ztlab/
sqlite3 /var/backups/ztlab/exo-*.db "SELECT COUNT(*) FROM files;"   # последняя
```

**Бэкап проверяется, а не просто создаётся.** Раньше копия снималась,
но никогда не восстанавливалась — неизвестно, была ли она пригодна.
Теперь:

- `backup.sh` пишет **манифест** рядом с копией: число строк в ключевых
  таблицах и количество файлов. Пустая база тоже «читается», поэтому
  сверка после восстановления — единственный способ убедиться, что
  вернулись именно те данные.
- Копия базы проверяется `PRAGMA integrity_check` сразу после снятия;
  битый файл удаляется, а не оставляется в ротации.
- `restore.sh` сначала проверяет копию в отдельном каталоге и сверяет
  её с манифестом, и только потом кладёт на место. Текущее состояние
  сохраняется как `exo-prerestore-*.db` — откат возможен всегда.
- Если текущая база уже нечитаема, `restore.sh` **не отказывается**
  работать: это и есть тот случай, когда восстановление нужно.

```bash
sudo /opt/ztlab/deploy/restore.sh /var/backups/ztlab/exo-20260929-031700.db --uploads
```

**Копия за пределами машины.** Бэкап на том же диске, что и данные, —
это не страховка, а копия. `backup-offsite.sh` дублирует копии на
другую машину; по умолчанию вывозится только база (килобайты),
файлы пациентов по сети не передаются, пока это не включено явно
через `OFFSITE_FILES=1`.

**Файлы пациентов.** Раньше `uploads` не копировались вообще — при
потере диска восстановить было нечего, кроме пустой базы. Теперь
`backup.sh` архивирует их и предупреждает, если на диске не хватит
места под архив.

## Проверка живости

`ztlab-health.timer` запускает проверку раз в две минуты. При сбое
счётчик растёт, на втором подряд — сервис перезапускается. Если и это
не помогло, приходит сообщение в Telegram, но не чаще раза в час:
одно и то же падение не должно завалить уведомлениями.

```bash
systemctl list-timers ztlab-*        # расписание
tail -f /var/log/ztlab-health.log    # журнал проверок
```

Telegram-уведомления зависят от `TELEGRAM_BOT_TOKEN` и
`TELEGRAM_CHAT_ID` в `/etc/ztlab/ztlab.env`.

## Обновление

```bash
git pull
sudo ./deploy/deploy.sh
```

Скрипт проверит версию Node и наличие секрета, снимет копию базы,
обновит код, выполнит `npm ci`, перезапустит сервис и проверит `/health`.

Откат: `git log`, затем `git checkout <коммит>` и `sudo ./deploy/deploy.sh`.
Копия базы перед обновлением снимается автоматически.

## Перенос 3D-файлов в S3

Пока файлы на диске ноутбука. Если ноутбук нельзя держать включённым
или диска не хватает, переключается без правки кода:

```
STORAGE_BACKEND=s3
S3_ENDPOINT=https://storage.yandexcloud.net
S3_BUCKET=ztlab-files
S3_KEY_ID=...
S3_KEY_SECRET=...
```

Своё хранилище в РФ важно: названия файлов могут содержать фамилии
пациентов, и данные не должны уходить за границу.

Перенос выполняется скриптом (отдельно), потому что файлов может быть
много, а процесс должен быть возобновляемым.

## Что закрыто и что нет

Закрыто: пароли (scrypt), разделение лабораторий на уровне запросов,
роли, ограничение попыток входа, HTTPS на VPS, брандмауэр,
запрет кэша авторизованных страниц, сессии в SQLite, бэкапы.

Не сделано и требует внимания перед запуском:

- **нет ограничения размера лаборатории.** Квота `STORAGE_QUOTA_GB`
  в конфиге есть, но не проверяется. Без неё лаборатория может занять
  весь диск.
- **нет срока действия триала и тарифов.** Нужно для оплаты.
- **нет восстановления пароля.** Сейчас пароль можно сменить только
  через администратора лаборатории.
- **удаление файла доступно любому сотруднику** (за кодом подтверждения).
  Решение осознанное: админ не всегда на связи, заказ не должен встать.
- **интерфейс не адаптирован под телефон.** Два шаблона по 700 строк
  рассчитаны на десктоп. Лаборатория пользуется с телефона.
