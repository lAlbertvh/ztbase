# Разработка на ноутбуке

Документ о том, как вести проект локально: где лежит код, как запустить,
как проверить и как не испортить рабочую копию на VPS.

---

## 1. Где лежит проект

```
/home/tapir/projects/ztbase
```

Это полный клон `git@github.com:lAlbertvh/ztbase.git`, ветка `master`.

Отдельная папка от прежней копии в `Документы/Default Project/exo`: та была
сделана до перехода на SQLite и к GitHub не подключена. Проверить
актуальность рабочей копии на компьютере с клиентами — отдельная задача,
см. раздел 8.

**Полный клон, а не `--depth 1`.** Откат в `deploy/README.md` описан как
`git log`, затем `git checkout <коммит>`. На неполном клоне этой истории
нет, и откат не выполнится — а он нужен в тот день, когда обновление
сломало выкладку.

## 2. Требования

| Что | Версия | Почему именно так |
|-----|--------|-------------------|
| Node.js | 22.x | У `better-sqlite3` нет готовой сборки под Node 26, а исходники не собираются: в Node 26 движок V8 убрал `info.This()` |
| npm | из состава Node 22 | Ставить отдельно не нужно |

Версия закреплена в трёх местах, чтобы расхождение было невозможно:
`.nvmrc` — файл `22`, `package.json → engines.node` — `22.x`,
цели сборки `pkg` — `node22-*`.

Проверка:

```bash
node -v          # v22.x
cat .nvmrc       # 22
```

**Важно про PATH.** В ноутбуке Node 20 стоит раньше системного Node 22:

```bash
echo $PATH | tr ':' '\n' | head -3
```

Если первым идёт `~/.local/node/v20/bin`, версия для тестов и запуска
не та. Node 20 был нужен только для сборки `pkg`, и держать его в PATH
постоянно незачем. Перед `npm test` и `npm start`:

```bash
export PATH=/usr/bin:$PATH
node -v          # должно быть v22.x
```

## 3. Установка

```bash
cd /home/tapir/projects/ztbase
npm ci
```

`npm ci`, а не `npm install`: берёт точные версии из `package-lock.json`.
Между двумя машинами разница в версиях — это разница в поведении.

## 4. Запуск

```bash
export SESSION_SECRET=$(node -e "console.log(require('crypto').randomBytes(32).toString('hex'))")
node server.js
```

Приложение откроет `http://localhost:3000` и само запустит браузер
(в режиме разработки). Из другой машины в той же сети — по адресу
`http://192.168.1.152:3000`.

Данные по умолчанию рядом с кодом: `database/exo.db` и `uploads/`.
Обе папки в `.gitignore`.

### Отдельная копия данных для экспериментов

Проверять миграции и новые маршруты на боевой базе нельзя: необратимо.
Запуск с отдельными каталогами:

```bash
export SESSION_SECRET=local-dev
export DB_DIR=/tmp/ztlab-dev/database
export UPLOAD_DIR=/tmp/ztlab-dev/uploads
export CONTENT_DIR=/tmp/ztlab-dev/content
export HOST=127.0.0.1
export PORT=3200
export NODE_ENV=production     # иначе приложение потребует SESSION_SECRET из боевого config
export OPEN_BROWSER=0
node server.js
```

Проверка: `curl -sf http://127.0.0.1:3200/health`

## 5. Тесты

```bash
npm test          # 473 проверки, девять наборов, 3–4 минуты
npm run test:unit # только быстрые юнит-тесты, несколько секунд
```

Отдельные наборы:

```bash
npm run test:quota
npm run test:live
npm run test:storage
npm run test:setup
npm run test:chat
npm run test:clinics
```

Живые тесты поднимают приложение сами на порту 3197. Если порт занят —
запусти на другом:

```bash
TEST_PORT=3200 npm test
```

**`npm test` перед каждым коммитом — обязателен.** Это единственная
страховка при правках на живом продукте с клиентом.

Полезно знать про `node --check`: он ловит только синтаксис. Свободная
переменная или неверный путь `require` проходят проверку и падают
вживую. При вынесении кода в новый модуль `--check` не замена тестам.

Тесты гоняются в CI при каждом пуше: https://github.com/lAlbertvh/ztbase/actions

## 6. Порядок работы над задачей

```bash
cd /home/tapir/projects/ztbase
git pull                       # забрать изменения, если работал на другой машине

# ... работа ...

npm test                       # 473 из 473

git status                     # проверить, что попадёт в коммит
git diff                       # прочитать каждое изменение

git add <файлы>                # не git add -A: так проще заметить лишнее
git commit                     # сообщение — см. раздел 7
```

Отдельно проверь, что в индекс не попало лишнее:

```bash
git status --short
```

В `.gitignore` лежат `database/`, `uploads/`, `*.db`, `*.db-wal`,
`*.db-shm`, `.env`. Если файл данных всё же проиндексирован, добавь его
в `.gitignore` и удали из индекса: `git rm --cached <файл>`.

## 7. Сообщения коммитов

Коммиты читаются как история решений. Формат — одна мысль, объяснение
почему, а не что.

Примеры из истории проекта:

- `Квота хранилища не проверялась. STORAGE_QUOTA_GB был в конфиге, но код его не читал`
- `Статика отдавалась как html: стиль, манифест и service worker`
- `Сервис не мог стартовать из-за ProtectSystem=strict`
- `Проверка: ходили на голый домен вместо www`

Что стоит писать в каждом коммите:

1. **Что сломалось или не работало.** Это главное: через год это
   единственное, что понадобится.
2. **Почему так вышло.** Ссылка на то, как было раньше.
3. **Что проверил.** «473 из 473», а не «всё работает».

Плохо: `исправил баг`, `небольшие правки`, `wip`.

Мелкие правки того же смысла объединяй в один коммит: коммит — это
одно изменение, которое можно откатить целиком.

## 8. Рабочая копия на компьютере с клиентом

Клиент работает с приложением на боевой машине. Перед правкой, которая
уходит туда:

1. Обновить боевую машину: `git pull` и `sudo deploy/deploy.sh`
2. **Не выкатывать на клиента непроверенное.** Общий порядок такой же,
   как при обновлении: `deploy.sh` снимает копию базы перед заменой кода.

Если на клиентской машине накопились изменения, которых нет в Git
(правки прямо на сервере), их нужно сначала забрать:

```bash
cd /var/lib/ztlab           # или куда там код
git status
git diff > /tmp/правки-клиента.patch
```

Это отдельная тема: правки на боевой машине опасны, их нужно
возвращать в репозиторий. Пока это не автоматизировано — проверяй
перед выкладкой.

## 9. Выкладка на VPS

Описана в `deploy/README.md`. Коротко:

```bash
# на VPS
git pull
sudo deploy/deploy.sh
sudo deploy/check.sh ztbase.ru
```

`deploy.sh` проверяет версию Node и наличие секрета, снимает копию базы,
обновляет код, выполняет `npm ci`, перезапускает сервис и проверяет
`/health`. Откат — `git checkout <коммит>` и повторный `deploy.sh`.

**Базу нельзя переносить `cp`.** Живая база работает в режиме WAL: рядом
с `exo.db` лежит `exo.db-wal`, и `cp exo.db` скопирует только главный
файл, молча потеряв всё, что в WAL. Правильно — через `sqlite3 .backup`
или готовой копией из `/var/backups/ztlab/`.

## 10. Чего делать нельзя

| Нельзя | Почему |
|--------|--------|
| Править файлы прямо на VPS | Изменения не попадут в репозиторий и пропадут при следующем `deploy.sh` |
| Делать `git add -A` | Легко унести в коммит `database/exo.db` или `.env` |
| Править `src/` на боевой машине | То же: перезапишется при обновлении |
| Менять пути из `src/config.js` без проверки сборки | В собранном `.exe` шаблоны лежат по внутреннему пути бандла, а данные — рядом с файлом; в разработке и то и другое совпадает, и ошибка видна только на собранном файле |
| Публиковать секреты | `.env` в `.gitignore`, но `SESSION_SECRET` и пароли SMTP не должны попадать и в историю |
