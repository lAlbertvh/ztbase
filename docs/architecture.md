# Архитектура

Карта модулей: кто за что отвечает и куда класть новый код.

---

## Слои

```
server.js              точка входа: собирает приложение и ничего не решает
  ↓
src/middleware/         сквозные проверки: сессия, роль, лимиты
  ↓
src/routes/             HTTP: читает запрос, отдаёт ответ или шаблон
  ↓
src/services/           предметная область: наряды, квоты, письма, триал
  ↓
src/db/                 SQLite: схема, миграции, обёртка query()
  ↓
SQLite (exo.db)
```

Правило: верхний слой знает о нижнем, нижний — о верхнем нет.
`src/routes/files.js` не знает, что такое `app.listen`; `src/services/quota.js`
не знает, что существуют HTTP-запросы.

Исключение — `src/config.js`: его читают все, включая `server.js`.

## server.js

375 строк. Только сборка приложения:

1. требует модули
2. поднимает Express, сессии, статику, multer
3. подключает `src/db` и получает `db`
4. подключает middleware и роутеры в правильном порядке
5. слушает порт

Если в `server.js` появляется логика — значит, ей место не там.
Правильный признак: маршрут длиннее 100 строк или появление `db.prepare`
внутри обработчика.

**Порядок подключения важен:**

```
health, lead          без сессии
auth.router           проверка сессии — после публичных маршрутов
orders, setup, …      рабочие разделы
password, auth-pages, trial   вход и триал
hub, files, users, titan       разделы интерфейса
titan                 последним: перехватывает /titan*
```

`/register-lab` живёт в модуле `trial`, а не `auth-pages`: в исходном
порядке он шёл сразу после экрана `/trial` и относится к сценарию
первого запуска.

Роутеры подключаются **без префикса** (`app.use(createFilesRoutes(…))`),
а не `app.use('/files', …)`. Причина: пути вроде `/titan/add` пришлось бы
переименовать в `/add`, и ссылки в шаблонах перестали бы совпадать с
адресами. При живом продукте с клиентом такая правка дороже, чем чуть
менее строгий стиль подключения.

## src/config.js

Пути, порт, лимиты. Единственное место, где живёт логика «где что лежит».

Ключевой момент: в собранном `.exe` шаблоны и статика лежат **внутри
бандла** (`__dirname` после `pkg`), а данные — **рядом с `.exe`**. В
разработке и то и другое указывает на папку проекта, поэтому ошибка в
этом файле видна только на собранном файле. Отсюда и `process.pkg` в коде.

## src/middleware/auth.js

Проверка сессии, роль, пробный период, незавершённая настройка,
счётчики попыток входа.

Порядок проверок задан осознанно:

1. **публичные адреса** — иначе страница входа потребовала бы входа
2. **сессия** — неавторизованный посетитель получает `/login`, а не экран
   оплаты чужой лаборатории
3. **пробный период** — проверяется после сессии по той же причине
4. **настройка** — только администратору, иначе врача уводило бы с чужой
   настройки

Счётчики входа и счётчики писем разные намеренно: сброс после успешного
входа не должен обнулять ограничение рассылки.

## src/db/

| Файл | Отвечает за |
|------|-------------|
| `index.js` | подключение, начальная схема, миграция из `files.db`, обёртка `query()` |
| `orders-schema.js` | пять связанных таблиц наряда |
| `manipulations-schema.js` | справочник манипуляций, чек-лист, журнал |
| `constructions-schema.js` | группы и позиции конструкций |
| `setup-schema.js` | мастер настройки, клиники-партнёры |
| `mail-schema.js` | одноразовые ссылки для входа и сброса |

Все миграции идемпотентны: вызов при каждом старте безопасен. Поэтому
нет номера версии схемы и таблицы «применённые миграции» — состояние
проверяется по факту наличия таблиц и колонок.

`query(sql, params)` возвращает `{ rows }` — API прежнего драйвера
PostgreSQL. Слой маршрутов написан под него, и переписывать сотни вызовов
ради смены базы было дороже, чем держать обёртку.

## views/

Шаблоны EJS. Логики в них быть не должно — если в шаблоне появляется
расчёт или запрос, его место в сервисе.

Самые большие: `orders/form.ejs` (604), `index.ejs` (756),
`titan.ejs` (594), `orders/show.ejs` (469). Это кандидаты на разбиение
на `partials/` при следующей правке.

## Куда класть новый код

| Хочу добавить | Файл |
|---------------|------|
| HTTP-маршрут | `src/routes/<раздел>.js` |
| Логику предметной области | `src/services/<домен>.js` |
| Таблицу или колонку | `src/db/<домен>-schema.js` |
| Проверку прав | `src/middleware/auth.js` |
| Переменную окружения | `src/config.js` **и** `deploy/ztlab.env.example` |
| Шаблон | `views/<раздел>.ejs` |
| Стиль | `public/css/app.css` |
| Тест на поведение | `test/<домен>-live.js` |
| Тест на функцию | `test/<домен>-unit.js` |
| Скрипт выкладки | `deploy/<что делает>.sh` + строка в `deploy/README.md` |

Переменная окружения, добавленная только в `src/config.js`, — частая
ошибка: на боевой машине её не будет, и код упадёт там, а не на тестах.

## Где хранится

| Что | Где | Примечание |
|-----|-----|------------|
| База | `/var/lib/ztlab/database/exo.db` | `DB_DIR`, режим WAL |
| 3D-файлы | `/var/lib/ztlab/uploads` | `UPLOAD_DIR` |
| Тексты сайта | `/var/lib/ztlab/content` | `CONTENT_DIR` |
| Картинки редактора | `/var/lib/ztlab/content/img` | `CONTENT_IMG_DIR` |
| Конфигурация | `/etc/ztlab/ztlab.env` | права 640, владелец `root:ztlab` |
| Копии | `/var/backups/ztlab` | 30 баз и 30 дней файлов |
| Код | `/opt/ztlab` | обновляется `deploy.sh` |

Код и данные разнесены намеренно: обновление не должно задевать базу и
файлы.
