# ZT Lab: план продукта

Документ фиксирует решения, принятые по итогам разговора с первым
клиентом 30 сентября 2026 и разбора прайс-листа лаборатории.

---

## 1. Что просит клиент

Основная боль: врач и техник работают в разных программах и
переписываются в мессенджерах. Из переписки потом вручную
пересоздаётся наряд — конструкции теряются, сроки и цены
договариваются устно.

Требуется:

1. **Врач заходит в приложение.** Сейчас в приложении только свои,
   внутри лаборатории. Врач — человек чужой организации.
2. **Чат врач ↔ техник.** Техник или администратор принимает заказ в
   работу, отвечает на сообщения, реагирует на комментарии.
3. **Наряд из чата.** Врач пишет: «отсутствуют 28, 17, 16, 45, 32,
   33, 34, пациент хочет имплантацию». Техник отвечает:
   «рекомендую съёмную конструкцию 17, 16, импланты вместо 28, 34,
   32, между ними мост из циркона». После согласования — кнопка
   **«Сформировать наряд»**, в которой договорённые конструкции стоят
   первыми в списке.
4. **Переписка внутри наряда.** Обсуждение этапов, цен и сроков в
   личном кабинете: открыл наряд → основная информация → диалог с
   врачом.
5. **SMS-уведомления.** Врач и техник оставляют номера, приходят
   «наряд № такой, вам сообщение от техника».

## 2. Тарифы

| Тариф | Цена | Кого помещается | Что включено |
|-------|------|-----------------|--------------|
| Минимальный | 500 ₽/мес | до 5 пользователей | наряд, справочник конструкций, роли |
| Про | обсуждается | до 15 пользователей | полноценный чат с врачом |
| Индивидуальный | по договору | любое число | доработки, вплоть до ИИ-ассистента |

В состав пяти пользователей входят техники, врачи и администраторы в
любой пропорции — отдельной тарификации по ролям нет.

**ИИ-ассистент** — направление индивидуальной версии: замена
бухгалтера или кладовщика, ежедневные отчёты. Например, ИИ считает
выработку и выпускает отчёт раз в день вместо ручного подсчёта.

**Демо-доступ с сайта** — способ попробовать продукт до оплаты.

Цена считается **за пользователя, который купил и установил
программу**; тариф задаёт потолок по числу пользователей, а не цену
одной подписки.

## 3. Роли пользователей

Две колонки, а не плоский список из пятнадцати значений: права
считаются проще, а специализация остаётся видимой.

| Роль | Специализация |
|------|---------------|
| врач | стоматолог-терапевт, стоматолог-ортопед, стоматолог-хирург, стоматолог-ортодонт |
| техник | съёмные протезы, металлист, CAD/CAM, гипсовщик, фрезеровщик, керамист |
| администрация | администратор, директор, бухгалтер, склад |

## 4. Клиника — полноценная сущность

Принято решение: клиника заводится как отдельная сущность.

- У клиники свои пользователи-врачи, у лаборатории — свои.
- Наряд принадлежит паре «клиника → лаборатория».
- Лаборатория видит только тех клиник, которые к ней обращались.
- Один врач работает с несколькими лабораториями без дублирования
  учётных записей.

Следствие: контроль доступа меняется во всех экранах. Сегодня всё
привязано к `lab_id`, и появление второй организации требует
пересмотра прав, а не точечных условий.

### Как это сделано

Клиника принадлежит одной лаборатории: `clinics.lab_id`. Общего
справочника клиник нет — у каждой лаборатории свой список, и клиника
из чужого списка в наряд не попадёт.

Связь хранится в `orders.clinic_id` и `users.clinic_id`. Права врача:

| Кто | Что видит |
|---|---|
| администратор, техник | все наряды своей лаборатории |
| врач с клиникой | наряды своей клиники **и** свои |
| врач без клиники | только свои наряды |

Врачу нельзя подменить клинику ни в URL, ни в форме: она берётся из
учётной записи. Администратор выбирает клинику из своего списка, и
подстановка чужого `clinic_id` отбрасывается.

Правило действует не только на списке: тем же `maySee` закрыты карточка,
правка, печать, QR и печать пачкой. У наряда может не быть клиники —
тогда он остаётся доступным автору и администратору.

Клиника с нарядами или врачами не удаляется, а отключается: иначе
наряды потеряли бы владельца, а врачи — привязку. Отключённую клинику
можно вернуть в работу. Пустую удаляют целиком.

Представитель клиники — это врач. Учётная запись заводится прямо в
`/setup/clinics` паролем от 6 символов; контакт без пароля остаётся
строкой справочника. Контакт со своей учётной записью считается в
тарифе один раз, а не как сотрудник плюс представитель.

Старые наряды переносятся на клинику автора миграцией при старте
сервера: `orders.clinic_id IS NULL` и `users.name = orders.created_by`
внутри одного `lab_id`.

## 5. Дерево конструкций

Четыре группы верхнего уровня:

- **Терапия**
- **Ортопедия съёмная**
- **Ортопедия несъёмная**
- **Ортодонтия**

Каппы отнесены к **ортодонтии** — каппы для отбеливания, спортивные,
элайнерные, «Сплит», накусочные пластинки.

Редактор групп — таблица в админке: заголовок = группа верхнего
уровня, ячейка = конструкции.

### Текущее состояние кода

Справочник зашит в `src/services/dental-reference.js`. В нём
`WORK_KINDS` (строки 19-31) смешивает группы и конструкции в одном
плоском списке:

```js
{ kind: 'removable', title: 'Съёмная конструкция' },
{ kind: 'fixed',     title: 'Несъёмная конструкция' },
{ kind: 'crown',     title: 'Корона' },
```

«Съёмная» и «Несёмная» стоят на одном уровне с «Корона», хотя это
группы, а не конструкции. В боевой базе 12 записей
`manipulations` с пустым `work_kind`.

Второе смешение: `manipulations` — это не конструкции, а **операции**
(сканирование, моделирование, фрезерование, обжиг) с ценой за
каждую. Конструкций как сущности в базе нет.

Нужно развести три уровня:

1. **Группа** — терапия / ортопедия съёмная / ортопедия несъёмная /
   ортодонтия
2. **Конструкция** — коронка, мост, элайнер, иммедиат протез; то, что
   выбирают в наряде
3. **Операция** — то, что уже есть в `manipulations`

### Дефекты исходных данных

Это нужно устранить до импорта, иначе в прайсе будут ошибки:

1. **Раздел 104xxx отсутствует целиком** — между 103 и 105 пустой
   номер. Либо позиции потеряны, либо в прайсе был пропуск.
2. **Коды с шестью цифрами вместо шести** — `1080120` и `1130120`
   выбиваются из ряда, где номер раздела трёхзначный (`1` + `08` +
   `120`). Похоже на опечатку ввода: должно быть `108120` и
   `113120`.
3. **Пропуски внутри разделов**: 107010 и 107020 отсутствуют, раздел
   начинается с 107030; в 108 нет 108010; в 121 нет 121130+.
4. **Колонка «срок» повреждена.** Значения вида `5+3`, `5+5` читаются,
   но встречаются слипшиеся `21`, `31` — вероятно, это два числа в
   одной ячейке (срок и этап) или срок и номер. Разбирать по такой
   таблице сроки нельзя.
5. **Ортодонтии в прайсе практически нет.** Только каппы и
   репозиционирование под элайнеры. Ни ретейнеров, ни трейнеров, ни
   брекет-систем, ни миофункциональных аппаратов, ни
   ортодонтических пластин — а именно это планировалось в группу
   «Ортодонтия».
6. **Терапии в прайсе нет.** Ни индивидуальных капов, ни силиконовых
   форм для реставрации как позиций. Каппа для отбеливания (121030)
   относится к каппам, то есть к ортодонтии.
7. **Цены «-» и «*»** — у 12 позиций вместо цены символ. Требуется
   расшифровка: то ли «по запросу», то ли «звонок», то ли цена
   согласована индивидуально.
8. **Стоимость часа в конце**: «Компаьютерное моделирование /
   репозиционирование зуба Cad/Cam +15% от стоимости». Это правило,
   а не позиция прайса.

Отдельно: цены надо вносить из чистого файла. Вставка в чат потеряла
выравнивание колонок, и ручной перенос ~230 позиций почти
гарантированно даст сдвиг цены на соседнюю строку.

## 7. Модель данных

Схема ещё не утверждена. Черновик:

```sql
-- клиника: организация-заказчик
CREATE TABLE clinics (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  slug TEXT UNIQUE NOT NULL,
  name TEXT NOT NULL,
  phone TEXT, email TEXT,
  created_at TEXT DEFAULT (datetime('now'))
);

-- пользователь принадлежит клинике ИЛИ лаборатории
ALTER TABLE users ADD COLUMN clinic_id INTEGER;
ALTER TABLE users ADD COLUMN phone TEXT;
ALTER TABLE users ADD COLUMN specialization TEXT;
-- лаборатория-клиника: какая клиника работает с какой лабораторией
CREATE TABLE clinic_lab_links (
  clinic_id INTEGER NOT NULL,
  lab_id INTEGER NOT NULL,
  created_at TEXT DEFAULT (datetime('now')),
  PRIMARY KEY (clinic_id, lab_id)
);

-- группы конструкций и сами конструкции
CREATE TABLE construction_groups (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  code TEXT UNIQUE NOT NULL,
  title TEXT NOT NULL,
  sort INTEGER NOT NULL DEFAULT 0
);
CREATE TABLE constructions (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  group_id INTEGER NOT NULL REFERENCES construction_groups(id),
  code TEXT NOT NULL,        -- код из прайса, напр. 100010
  title TEXT NOT NULL,
  price REAL,
  term TEXT,                 -- срок изготовления
  sort INTEGER NOT NULL DEFAULT 0,
  active INTEGER NOT NULL DEFAULT 1,
  UNIQUE (code)
);

-- переписка
CREATE TABLE messages (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  lab_id INTEGER NOT NULL,
  clinic_id INTEGER NOT NULL,
  order_id INTEGER,          -- NULL до создания наряда
  author_id INTEGER NOT NULL,
  body TEXT NOT NULL,
  kind TEXT NOT NULL DEFAULT 'chat',  -- chat | comment | system
  created_at TEXT DEFAULT (datetime('now'))
);
CREATE INDEX idx_messages_thread ON messages(lab_id, clinic_id, order_id, id);

-- наряд принадлежит паре клиника -> лаборатория
ALTER TABLE orders ADD COLUMN clinic_id INTEGER;
ALTER TABLE orders ADD COLUMN created_by_user_id INTEGER;
```

Разбор сообщений: номера зубов по FDI и названия конструкций вытаскиваются
регулярными выражениями, без ИИ. «Да, делайте» алгоритмом не
определяется — кнопку «Сформировать наряд» жмёт человек, приложение
только подсвечивает, что договорённость вероятна.
